# ai系统 · 数据库设计说明

- 引擎：SQLite 3（原生 `sqlite3` 模块，无 ORM）
- 库文件：`backend/yuejiao.db`
- 建表基线：`backend/schema.sql`（全部 `CREATE TABLE IF NOT EXISTS`，可反复执行）
- 增量迁移：`backend/db.py` 的 `ensure_migrations()`，启动时执行 schema.sql 后再按 `MIGRATIONS` 字典补列，老库无需手工改结构
- 表数量：**21 张业务表**，分 5 个域

> 时间字段说明：`create_time DATETIME DEFAULT CURRENT_TIMESTAMP` 写入的是 **UTC**。情绪预警的去重逻辑改为显式写本地时间，两者不要混用比较。

---

## 一、核心用户域

### 1. sys_user — 统一用户表

学生、员工、客户、老师共用一张表，靠 `user_type` 区分。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| username | TEXT NOT NULL | 登录账号（学生可用手机号） |
| real_name | TEXT | 真实姓名 |
| user_type | TEXT | `STUDENT` / `EMPLOYEE` / `CUSTOMER` / `TEACHER` |
| contact_info | TEXT | 手机号或邮箱 |
| status | TEXT DEFAULT '正常' | 正常 / 禁用 |
| password_hash | TEXT | PBKDF2-SHA256 哈希。**无初始密码兜底**：为空即禁止登录（系统访客 `_guest` 就是这种无密码账号） |
| target_country | TEXT | 学生意向留学国家（v4 新增） |
| lifecycle_stage | TEXT DEFAULT 'CONSULT' | **学籍阶段**（v5 新增）：`CONSULT` 咨询期 / `APPLYING` 申请期 / `ENROLLED` 在读 / `ALUMNI` 已毕业。决定学生能用哪些模块，由 `service/lifecycle.py` 统一裁决 |
| token_version | INTEGER DEFAULT 0 | 改密、停用、启用、重置密码时递增，使旧 token 立即失效 |

**学籍阶段流转**

```
注册 → CONSULT ──员工建档──> APPLYING ──推进到「已入学」──> ENROLLED ──毕业──> ALUMNI
         │                      │                          │
      了解/报名             + 申请进度            + 请假/成绩/售后
```

- 升级自动：`application.create` 置 `APPLYING`，`application.advance` 到「已入学」置 `ENROLLED`。
- 手动可调：员工在「学生档案 → 调整阶段」直接设置（支持降级与标记毕业）。
- 老库回填：`ensure_migrations()` 会把已有请假/成绩/售后记录的学生自动设为 `ENROLLED`，避免上线门禁后老生被锁。

**账号初始化约定（v6：无演示账号）**

- 建库后 `sys_user` 为空，不再写入任何演示账号，也没有固定默认密码兜底。
- 第一个管理员由 `/api/auth/setup` 创建（仅当员工数为 0 时可用，密码 ≥8 位）；学生在页面自助注册。
- `_guest` 是系统访客账号（`user_type='CUSTOMER'`、`password_hash` 为空、不可登录），仅用于承接免登录客服的对话记录；首次调用 `/public-chat` 时自动创建。
- 员工忘记密码由管理员执行“重置密码”；停用、启用、改密和重置都会递增 `token_version`，旧 token 不恢复。

## 二、学生管家域

### 2. student_admin_service — 行政服务（请假）

| 字段 | 说明 |
|---|---|
| student_id | 申请人 |
| service_type | 业务类型，目前固定「请假」 |
| start_time / end_time | 请假起止（由 `time_parser` 从自然语言解析） |
| reason | 请假理由原文 |
| status | 待审批 / 已通过 / 已驳回 |
| approver_id | 审批人（员工/老师） |
| approver_comment | **审批留言 / 驳回理由**（v4 新增，驳回必填） |
| approve_time | 审批时间（v4 新增） |

### 3. student_psych_profile — 心理画像（一人一条）

`student_id` 唯一；`latest_emotion_tag`（高危/关注/正常）、`emotion_score`（0–100）、`emotion_history`（JSON 字符串，最多 50 条）、`last_interaction_time`（最近交互时间）。

### 4. student_psych_alert — 心理预警

情绪分达到阈值时写入，供员工后台看板处理。

| 字段 | 说明 |
|---|---|
| trigger_reason | 触发原话 |
| risk_level | 高 / 中 / 低 |
| emotion_score | 触发时的情绪分值（0–100） |
| status | 未处理 / 已解决 |
| handler_id / handle_note | 处理人与备注（v4 新增） |

### 5. student_feedback_ticket — 售后工单

`content` 摘要、`detail` 详情、`solution` 解决方案、`status` 状态、`is_notified` 是否已通知学生。

---

## 三、员工运营域

### 6. crm_lead — 意向客户（线索）

`customer_name`、`contact_info`、`background_info`、`follow_up_history`（JSON 追加）、`status`（新增意向/跟进中/已签约/已流失）、`owner_employee_id`（自动分配给线索最少的员工）。

### 7. employee_daily_report — 员工日报

`employee_id`、`report_date`、`content`。

### 8. student_score — 学生成绩

`student_id`、`course_name`、`score`（REAL，支持小数）、`semester`。

---

## 四、客服与活动域

### 9. event_lecture — 活动与讲座

留学方案和企业信息不在数据库保存，由 Dify 知识库实时提供。

`event_name`、`start_time`、`location`、`country`（v4 新增）、`description`（v4 新增）、`max_participants`（名额上限）、`current_participants`（当前报名数，防超卖）。

### 10. event_registration — 活动报名

对登录学生使用 `event_id + customer_id` 部分唯一索引，对访客使用 `event_id + contact_info` 部分唯一索引；报名使用 `BEGIN IMMEDIATE` 与条件更新防止超卖，并回写 `current_participants`、写 `notification`。

### 11. conversation_log — 对话记录

`user_id`、`agent_type`（学生/员工/客服）、`user_input`、`ai_output`、`emotion_tag`，用于后续数据分析与情绪回溯。

## 五、业务闭环支撑域（v4 新增）

### 12. application_progress — 留学申请进度

一条记录 = 一个学生的一次申请。

| 字段 | 说明 |
|---|---|
| student_id | 申请人 |
| country / university / program | 国家、院校、专业 |
| stage | 当前阶段：选校定位 → 材料准备 → 递交申请 → 面试 → Offer → 签证 → 行前 → 入学 |
| stage_detail | 阶段说明 |
| status | 进行中 / 已完成 / 已暂停 |
| operator_id | 最近更新的员工 |
| update_time | 最近更新时间 |

### 13. application_history — 申请阶段操作日志

每次 `stage` 变更写一条，`application_id` 关联主表，形成学生端可见的时间轴。

| 字段 | 说明 |
|---|---|
| application_id | 关联申请 |
| stage | 到达的阶段 |
| note | 本阶段说明 |
| operator_id | 操作人 |
| action | 创建申请 / 推进阶段 / 完善档案 / 上传材料 / 审核材料等 |
| source_type | MANUAL 真实操作 / BACKFILL 历史回填 / SYSTEM 系统生成 |
| related_material_id | 关联材料 |
| detail_json | 本次操作的结构化快照 |

### 14. application_stage_record — 八阶段档案

每个申请固定形成 8 条阶段记录，保存阶段状态、结论、结构化明细、开始/完成时间和来源。

| 字段 | 说明 |
|---|---|
| application_id + stage | 一次申请的一个具体阶段，联合唯一 |
| status | 待进行 / 进行中 / 已完成 / 待补充 |
| summary | 学生可见的阶段结论 |
| detail_json | 院校、申请编号、面试、Offer、签证、行前等结构化字段 |
| started_at / completed_at | 阶段开始与完成时间 |
| source_type | MANUAL 真实录入 / BACKFILL 历史回填 / SYSTEM 系统生成 |

### 15. application_material — 申请材料与附件

材料清单与附件元数据。文件正文位于 `backend/uploads/application_materials/`，SQLite 只存引用。

| 字段 | 说明 |
|---|---|
| application_id / stage | 所属申请和阶段 |
| material_name | 材料名称 |
| required_flag | 是否必需 |
| status | 待提交 / 待审核 / 已通过 / 已退回 |
| file_name / storage_name / mime_type / file_size | 原文件名、随机存储名、类型和大小 |
| review_note / reviewed_by | 审核意见和审核人 |
| uploaded_by / version | 上传人和附件版本 |
| visible_to_student | 内部材料可对学生隐藏 |

### 16. notification — 站内通知

| 字段 | 说明 |
|---|---|
| user_id | 接收人 |
| type | 审批 / 预警 / 活动 / 申请 / 系统 |
| title / content | 标题与正文 |
| is_read | 0 未读 / 1 已读 |
| link_page | 点击后跳转的页面锚点 |

触发来源：请假审批结果、预警处理、活动报名成功、申请阶段更新、线索分配给员工。

## 六、表关系速查

```
sys_user (1) ──< student_admin_service (N)            学生请假
sys_user (1) ──  student_psych_profile (1)            心理画像
sys_user (1) ──< student_psych_alert (N)              情绪预警
sys_user (1) ──< student_feedback_ticket (N)          售后工单
sys_user (1) ──< student_score (N)                    成绩
sys_user (1) ──< application_progress (N)             申请进度
application_progress (1) ──< application_history (N)  阶段时间轴
application_progress (1) ──< application_stage_record (8)  阶段明细
application_progress (1) ──< application_material (N)  材料与附件
sys_user (1) ──< crm_lead (N)                         员工作为线索负责人
event_lecture (1) ──< event_registration (N)          活动报名
sys_user (1) ──< notification (N)                     站内通知
```

外键仍由应用层维护；数据库已对用户名、状态、用户关联、心理画像和报名组合建立索引，并对用户名与报名组合建立唯一约束。
