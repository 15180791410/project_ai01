# ai全角色权限矩阵与验收说明

更新时间：2026-11-18

## 1. 权限设计原则

权限分为两层，任何一层不满足都必须拒绝：

1. **功能权限**：当前角色能不能使用某类功能；
2. **数据归属**：当前员工能不能操作这一条具体记录。

权限矩阵由 `backend/service/rbac.py` 统一定义。前端菜单和按钮隐藏只用于改善体验，
真正的安全边界在 FastAPI 接口和 SQL 数据范围中。

角色采用两层模型：账号类型是 `EMPLOYEE`，员工子角色是
`ADVISOR / HOMEROOM / LEADER`。顾问、班主任、领导不是三个独立账号类型，
而是同一个员工体系下的工作分工。

## 2. 角色职责

| 角色 | 可以做什么 | 明确不能做什么 |
|---|---|---|
| 学生 | 本人资料、请假、售后、成绩、心理画像、活动报名、主动申请就读 | 查看其他学生、员工后台、客户线索 |
| 员工·顾问 ADVISOR | 员工公共能力、本人客户线索、本人负责学生、本人申请/成绩/售后、本人学生预警只读、Dify方案只读 | 审批请假、处理预警、调整学籍阶段、管理活动/账号、写入方案 |
| 员工·班主任 HOMEROOM | 员工公共能力、本人班级学生、请假审批、心理预警、售后、成绩、查看申请、Dify方案只读 | 查看 CRM、推进申请、调整学籍阶段、管理活动/账号、写入方案 |
| 员工·领导 LEADER | 员工公共能力、全部业务查看与推进、审批、预警、CRM、申请、成绩、阶段调整 | 管理后台账号、新增/编辑/删除活动；留学方案只能在 Dify 维护 |
| 管理员 ADMIN | 全部业务、内容配置、员工账号和角色管理 | 无业务功能限制；停用自己账号仍被单独禁止 |
| 维护人员 MAINTAINER | 健康检查、运行状态、本人账户 | 学生、客户、请假、成绩、心理预警、账号清单等业务隐私 |
| 访客 CUSTOMER / 公开用户 | 公司知识库问答、活动与方案查询、活动报名、咨询留资 | 员工后台、任何已登录用户私有数据 |

## 4. 关键越权修复

- 班主任不能新增、修改或删除活动和留学方案；这些是系统内容配置，只属于管理员。
- 班主任不能查看客户线索，也不能通过 NL2SQL 查询客户统计。
- 班主任审批请假或处理预警前，必须校验学生 `homeroom_id` 属于本人。
- 顾问不能审批请假、处理心理预警或修改学籍阶段；可只读本人负责学生的预警。
- 顾问只能创建和推进本人 `advisor_id` 学生的申请。
- 顾问和班主任的工作台统计只计算本人数据范围，不再返回全公司数字。
- 领导可以查看和推进全部业务，但不能管理员工账号或修改活动；留学方案只能在 Dify 维护。
- 维护人员被排除在所有业务接口之外，只能访问健康状态和本人账户。
- `/api/auth/staff` 仅管理员可调用，普通员工不能枚举全公司账号和联系方式。
- `/api/auth/users?role=STUDENT` 对顾问和班主任自动按负责学生过滤。
- 活动报名名单对顾问只返回本人负责学生，访客报名仅领导和管理员查看。
- 留学方案即使由管理员勾选“已核实”，后端仍会实时检索 Dify；国家、项目模式和来源文档必须同时命中，否则只能保存为未核实草稿。
- 管理员登录一次后可在同一后台切换管理员、员工（顾问/班主任/领导）和维护人员视图；切换后权限立即收紧，低权限视图不能管理账号或修改安全信息。
- 成绩查询返回学生姓名、账号、意向国家，并支持姓名/账号、国家和课程组合筛选。
- 学生档案支持国家/地区、留学方案、学籍阶段、培养计划和姓名/账号筛选。
- 员工拥有工作日报、客户录入、成绩录入、预警协同和通知等完整操作入口。

## 5. Dify 权限链路

所有 Dify 工具仍调用 FastAPI，不在 Dify 内另建权限副本：

```text
前端 -> FastAPI 代理 -> Dify 工作流 -> 自定义工具 -> FastAPI 权限校验 -> SQLite
```

如果 Dify 工具收到 403，工具节点使用 `default-value` 降级策略进入回答节点，
明确告诉用户“当前角色无权执行此操作或服务暂不可用”，不会中止整张工作流，
也不会猜测或补全业务数据。

## 6. 验收结果

确定性业务回归：161/161 通过；Dify question-classifier、LLM 画像抽取、知识库和三条业务工作流已真实联调。

新增覆盖：

- 班主任新增/删除活动被拒；
- 班主任新增留学方案被拒；
- 班主任查询客户线索被拒；
- 班主任审批其他班级请假被拒；
- 班主任处理其他班级预警被拒；
- 班主任通过 NL2SQL 查询客户被拒；
- 知识库没有依据的“加拿大本科班”不能标记为已核实；
- 顾问查看请假、心理预警、修改学籍阶段被拒；
- 领导查看业务数据成功、管理员工账号和修改内容被拒；
- 维护人员读取业务隐私被拒；
- 管理员执行全量业务和账号管理成功；
- Dify 推荐直接返回项目和匹配度，并只引用知识库片段；
- Dify 无权工具调用不再报“服务不可用”，而是返回明确无权限提示。
- 申请必须逐阶段推进，不能从选校定位直接跳到已入学；直接设置学籍为在读时，系统会按顺序补齐申请时间轴并明确标注“系统补记”。

## 7. 仍需注意的边界

当前项目仍是单机 SQLite、单后端进程的课程/演示架构。企业生产环境还应继续补充：

- PostgreSQL/MySQL 与数据库备份恢复演练；
- Redis 会话、登录失败限流、验证码和密码找回二次验证；
- 审计日志与管理操作不可抵赖；
- HTTPS、反向代理、密钥托管和容器化部署；
- 更大规模下的知识库召回评测与人工审核流程。
