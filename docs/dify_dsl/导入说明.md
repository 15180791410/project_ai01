## 二、工具集是怎么生成和同步的

### 2.1 生成（唯一事实来源 = 后端 OpenAPI）

```bash
cd backend
python -c "import main,json;json.dump(main.app.openapi(),open('../docs/dify_dsl/_openapi_source.json','w',encoding='utf-8'),ensure_ascii=False)"

cd ../docs/dify_dsl
python build_tools.py
```

产出：

- `yuejiao_api_tools.yaml` —— 可手工在 Dify 控制台「工具 → 从 OpenAPI 导入」的完整定义
- `live/tools_str_new.json` —— Dify 数据库 `tool_api_providers.tools_str` 的等价结构

`build_tools.py` 里维护两份表：

- `OPERATIONS`：路径 + 方法 → 工具名（operationId）。**旧工具名保持不变**，所以老工作流节点不会失效。
- `PARAM_DESC` / `TOOL_DESC`：参数与工具的中文语义描述。Dify 把这些描述喂给 LLM，
  描述写得好不好直接决定工具能不能被正确调用，新增接口时务必补。

### 2.2 同步到运行中的 Dify（免手工导入）

```bash
cd docs/dify_dsl
python publish_runtime.py --apply
```

同步后校验：

```sql
SELECT json_array_length(tools_str::json) FROM tool_api_providers
WHERE id = '1c2de193-75e4-4c78-8366-99b5f4e1ca00';   -- 应为 52
```

> 若是在**另一套 Dify** 上部署，请走控制台导入 `yuejiao_api_tools.yaml`，
> 并把 `patch_workflows.py` 里的 `PROVIDER_ID` 换成你那边工具集的真实 UUID。

## 三、工作流是怎么生成和发布的

```bash
cd docs/dify_dsl
python patch_workflows.py
python patch_leave_orchestration.py
```

两个脚本依次完成：

1. 读取 `live/<app>_draft.json`（从 Dify 数据库导出的**真实图**）
2. 按 `STUDENT` / `EMPLOYEE` / `CUSTOMER` 三份配置重建意图分类：
   每个分支 = **Question Classifier → 工具节点 → LLM 整理 → 直接回复**
3. 为学生工作流补入请假上下文、LLM 字段提取、`prepare_leave`、条件分支、复述确认和 `confirm_leave`
4. 输出 `live/<app>_new.json` 与可导入的 `<app>_workflow.yml`

写回数据库并发布（推荐使用统一脚本）：

```bash
python publish_runtime.py          # 仅生成 live/update_runtime.sql
python publish_runtime.py --apply  # 更新本机 Dify 并重启 API/Worker
```

脚本同时更新工具集、草稿行和已发布行，并在写入前校验工具数量与空图。生产环境执行前必须先备份 Dify PostgreSQL。

## 三之二、回复风格与响应速度（必读）

### 3.1 为什么要单独做这件事

qwen3 系列默认带「深度思考」，节点上原本写着：

```json
{"enable_thinking": true, "reasoning_effort": "xhigh"}
```

后果有两个，都很致命：

1. **慢**：每次回答先推理到 xhigh 档，简单问题也要十几秒到半分钟；
2. **脏**：思考内容会跟着 `answer` 一起返回，用户看到的就是 `### 思考过程`、`**调用工具**` 这类东西。

另外模型天然爱输出 markdown，前端按纯文本渲染时，`###`、`**`、`-` 会原样露出来，读起来很不专业。

### 3.2 当前样式状态

正式流程由 `patch_workflows.py` 在重建时统一为所有 LLM 节点关闭深度思考，
并追加输出规范。已删除旧的 `fix_style.py` 和 `live/fix/` 一次性工作区。

### 3.3 输出规范的具体内容

追加在每个 LLM 节点 system 提示词末尾，`patch_workflows.py` 里的 `STYLE_TEXT` 与此一致，
**重建工作流时会自动带上**，不会因为重跑脚本而退回旧状态：

```
【输出规范（必须遵守）】
1. 直接回答问题，只给结论和要点，不要输出思考过程、推理步骤、计划、工具调用说明，
   也不要出现"正在查询""根据工具返回""数据库显示""作为 AI"这类话。
2. 用简体中文自然分段，像同事面对面说话。禁止使用任何 markdown 符号：#、##、*、**、_、`、>、|、---。
3. 需要罗列时用「1. 2. 3.」或「· 」，需要强调时用「」，不要加粗。
4. 回答尽量控制在 6 行以内；用户明确要求详细时才展开，展开也分短段。
5. 不要重复用户的问题，不要加"当然可以""希望以上回答对你有帮助"这类客套开头结尾。
```

### 3.4 三道闸门，缺一不可

| 层 | 位置 | 作用 |
|---|---|---|
| 提示词 | Dify LLM 节点 system | 从源头要求纯文本、直接回答 |
| 后端清洗 | `backend/api/auth.py` 的 `_clean_answer()` | 兜底剥掉 `think/thinking/reasoning` 标签、"正在调用工具""工具返回"整行、"作为 AI"自述、连续空行 |
| 前端渲染 | `frontend/static/common.js` 的 `renderMarkdown()` | 万一模型仍输出 markdown，就渲染成真标题/列表/表格，肉眼看不到符号 |

实测（关闭思考后，本机 Dify + 通义 qwen3.8-max）：

| 场景 | 耗时 | 输出 |
|---|---|---|
| 学生问「新加坡留学一年费用大概多少」 | 3.7s | 纯文本三段 + 「1. 2. 3.」，无符号 |
| 客服问「报名需要准备哪些材料」 | 4.2s | 分项目说明，无符号 |

> 若以后换模型或换工作流，重新执行 `patch_workflows.py`，再检查生成图中的
> LLM 节点是否仍包含 `STYLE_TEXT` 和 `enable_thinking=false`。

## 四、关键：GET 使用 Authorization，POST 使用 body token

v2 新增的接口（申请进度、我的报名、通知、请假审批、线索跟进、报名名单、学生国家分布…）都要求登录令牌。
传递链路：

```
前端登录 → 后端 /api/auth/dify-chat
        → inputs = { student_id / employee_id, auth_token: <登录token> }
        → 工作流开始节点变量 auth_token（text-input）
        → GET 工具 authorization 参数填 Bearer {{#start_node.auth_token#}}
        → POST 工具 token 参数填 {{#start_node.auth_token#}}
```

相关代码：

- `backend/api/auth.py` 的 `dify_chat()` 把 `auth_token` 一起传给 Dify
- `patch_workflows.py` 的 `add_auth_token()` 在开始节点声明该变量
- 工具定义里 `token` 参数的描述已写明「由 auth_token 传入」

**因此后端必须重启一次**，让 `dify_chat()` 的新代码生效：

```powershell
cd C:\Users\Windows\Desktop\yuejiao_project\backend
.\start_server.ps1
```

`start_server.ps1` 默认开启热重载；端口已占用时会安全退出，不会强制结束其他进程。

> 免登录的客服工作流不使用 token，只调用公开接口（活动列表、留学方案、课程项目）。

## 五、新手最容易踩的四个坑

### 1）工具节点的 `provider_id` 必须是 UUID

填工具集名称 `yuejiao_api` 会报：

```
invalid input syntax for type uuid: "yuejiao_api"
WHERE tool_api_providers.id = 'yuejiao_api'::UUID
```

现象是工具节点一直转圈。查询真实 UUID：

```sql
SELECT id, name FROM tool_api_providers WHERE name='yuejiao_api';
```

### 2）后端必须监听 `0.0.0.0`

只监听 `127.0.0.1` 时，Dify 容器通过 `host.docker.internal` 连不进来，同样表现为工具节点卡住。
`start_server.ps1` 已固定为 `--host 0.0.0.0`。

### 3）开始节点变量类型

Dify 只接受 `text-input / number / paragraph / select / file / checkbox` 等枚举值。
写 `"type": "string"` 会直接 400：

```
1 validation error for VariableEntity  type  Input should be 'text-input', ...
```

字符串变量请用 `text-input`，数字用 `number`。

### 4）意图分类使用语义优先级

Question Classifier 由 LLM 根据完整语义选择业务类别，生成器会把每类关键词写入
类别名称和 instruction，并保留“高风险情绪优先、查记录优先于新增、知识咨询优先于办理”
的业务优先级。修改类别时需同步检查这些规则。

成绩、售后、活动、客户查询和推荐等关键办理接口仍由 FastAPI 做最终业务拦截。
学生请假使用独立编排链路：Dify 分类和 LLM 提取 → `prepare_leave` →
条件追问/确认 → `confirm_leave`。正常链路只有 Dify 不可用时才允许后端
确定性处理器降级。当前生成器已经按此规则整合：

- 学生：15 个业务分支 + 1 兜底，保留高风险情绪最优先和请假草稿续办；
- 员工：12 → 10 个分支，审批帮助与普通知识问答共用知识库链路；
- 客服：活动枚举从 27 条缩为 6 条，推荐枚举从 34 条缩为 10 条。

## 七、验证方式

不经过前端，直接打 Dify Service API 即可验证某个意图是否命中正确工具：

```bash
curl http://localhost:5001/v1/chat-messages \
  -H "Authorization: Bearer <学生应用的 API Key>" \
  -H "Content-Type: application/json" \
  -d '{"inputs":{"student_id":1,"auth_token":"<登录拿到的token>"},"query":"我的申请进度到哪一步了","response_mode":"blocking","user":"t1"}'
```

已验证通过的样例：

| 场景 | 提问 | 命中工具 | 结果 |
|---|---|---|---|
| 学生·成绩 | 查一下我的成绩 | `my_scores` | 返回真实成绩列表 |
| 学生·请假记录 | 看看我的请假记录 | `my_leaves` | 返回记录 + 审批意见 |
| 学生·请假办理 | 我下周一到下周三请事假，家里有事 | `prepare_leave` → 确认 → `confirm_leave` | 先复述，确认后才写正式请假单 |
| 学生·申请进度 | 我的申请进度到哪一步了 | `my_applications` | 返回 2 条档案与时间轴 |
| 学生·活动 | 最近有什么活动讲座 | `content_events` | 返回后台当前已发布活动；旧演示活动已清空 |
| 客服·公司员工活动 | 公司有哪些员工活动 | 知识库检索 | 返回团建、中秋晚会、年度晚宴等知识库原文 |
| 客服·研学活动 | 公司有哪些研学活动 | 知识库检索 | 返回主题线路、定制研学、国际研学等知识库原文 |
| 员工·待审批 | 有哪些待审批的请假 | `pending_leaves` | 返回待审批列表 |
| 员工·国家分布 | 各意向国家有多少学生 | `students_by_country` | 德国 1 / 新加坡 1 / 未填写 6 |
| 客服·留学方案 | 你们有哪些留学方案 | `list_programs` | 返回 6 个方案 |
