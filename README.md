# 粤教服务智能助手
基于 FastAPI + 前端页面的企业智能助手项目，面向教育服务场景，提供问答、内容管理、员工后台、客户服务等能力。
## ✨ 项目结构
面向留学服务机构的智能体业务平台：企业官网获客 → 学生服务 → 员工运营 → 客服答疑，四端由 FastAPI + SQLite + Dify Chatflow 驱动。

本轮安全加固、Dify 同步、验收结果与备份位置见 [`docs/整改验收报告.md`](docs/整改验收报告.md)。
第一次阅读源码请先看 [`docs/代码阅读指南.md`](docs/代码阅读指南.md)。

## 一分钟了解

| 层 | 技术 | 位置 |
|---|---|---|
| 后端 | FastAPI + 原生 sqlite3，单进程 `0.0.0.0:8000` | `backend/` |
| 前端 | 纯静态 HTML + 原生 JS，无构建、无 npm | `frontend/` |
| 智能体 | Dify 1.10 Chatflow：3 张工作流 + 50 个自定义工具 | `docs/dify_dsl/` |
| 数据 | SQLite，21 张业务表；知识库主数据不落库 | `backend/yuejiao.db`（基线 `schema.sql`） |

## 快速开始

```powershell
# 1. 装依赖（Python 3.10+，已在 3.13 验证）
pip install -r requirements.txt

# 2. 起后端（端口被占用时安全退出，不会强杀其他进程）
cd backend
.\start_server.ps1
# 需要换端口：.\start_server.ps1 -Port 8001
# 若被执行策略拦截，先跑：Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

# 3. 通过稳定 HTTP 地址打开前端
# 推荐 127.0.0.1；密码管理器可识别并保存该站点的登录信息。
start http://127.0.0.1:8000/
# 员工后台：http://127.0.0.1:8000/admin.html
# 学生工作台：http://127.0.0.1:8000/student.html
```

后端起来后可访问 `http://127.0.0.1:8000/docs` 查看 81 个业务路径、82 个业务操作的 Swagger 文档；`/health` 和需求规格兼容路径 `/api/health` 均返回系统状态。

> 前端现在由 FastAPI 同源托管，`static/common.js` 在 HTTP 页面中自动使用
> `location.origin`，不再依赖固定 API 地址。请使用
> `http://127.0.0.1:8000/...`，不要直接双击 `file://` HTML；浏览器密码管理器
> 通常不会为本地文件页面保存账号密码。

## 首次使用：没有内置账号，先初始化

系统**不预置任何演示账号**，数据库里也没有可登录的初始用户，避免上线后被人拿默认密码进后台。第一次启动按以下顺序建立账号：

**① 创建管理员（仅一次）**
打开 `frontend/admin.html`，若库里还没有管理员账号，页面会自动切换到「首次初始化」向导：填账号、姓名、至少 8 位密码和安全问题，提交后自动登录后台。
这一步只为系统创建第一个 ADMIN；初始化完成后接口会拒绝再次创建初始管理员。

> 如果部署在可被访问的服务器上，建议先设置环境变量 `YUEJIAO_SETUP_CODE=你的口令`，初始化时必须同时填对，防止被他人抢注管理员。

**② 给学生开户**
学生在 `frontend/student.html` 自助注册即可（账号 ≥3 字符、密码 ≥6 位），注册后直接进入学生工作台。

**③ 继续加同事**
管理员进入「用户中心 → 员工账号」新增员工（密码 ≥8 位），也可停用/启用离职或调岗的同事。停用后立即无法登录，历史数据保留。

> 密码找回：新账号注册时设置安全问题，可在登录页自助找回；旧账号登录后可在用户中心补设；管理员也可重置员工密码。系统不保存或展示明文密码。

运行测试时可设置员工账号：`set YUEJIAO_EMP_USER=你的账号` 与 `set YUEJIAO_EMP_PASS=密码`。若系统尚未初始化，测试会临时创建 QA 管理员，并在结束后只删除本轮 QA 账号和精确 ID 数据。

## 学生生命周期：服务是渐进解锁的

学生注册后不会立刻拥有全部功能，而是跟着学籍阶段走：

| 阶段 | 学生状态 | 能用什么 | 不能用什么 |
|---|---|---|---|
| `CONSULT` 咨询期 | 刚注册，还没定方向 | 智能助手、留学方案、活动报名、主动申请就读 | 请假、成绩、售后、心情记录 |
| `APPLYING` 申请期 | 顾问已建档 | 上一步 + 申请进度时间轴 | 请假、成绩、售后、心情记录 |
| `ENROLLED` 在读 | 已入学 | 全部 | — |
| `ALUMNI` 已毕业 | 完成学业 | 只读查询 | 请假、新申请 |

设计原则是**可读的开放、可写的收紧**：看方案、问助手随时可用；请假、售后、成绩和心情记录必须到在读阶段，后端返回引导话术而不是冷冰冰的“无权限”。咨询期/申请期使用智能助手时仍保留高危安全检测，但不会把内容写入学生心理画像历史。

### 生命周期完整记录

- `student_lifecycle_event`：只追加的生命周期流水，记录原阶段、目标阶段、生效日期、原因、操作人角色和纠错来源。
- `student_enrollment`：入学档案快照，保存项目、入学日期、标准学制、预计毕业日期和缺失项状态；后续知识库变化不回写历史档案。
- `student_graduation_request`：毕业审核流水。只有在读学生可发起，班主任、管理员或领导审核通过后，学籍才转为 `ALUMNI`。
- 正常流程只能逐级前进：咨询期 → 申请期 → 在读 → 已毕业。管理员纠错必须显式 `force`、填写原因并留下 `ADMIN_CORRECTION` 流水。
- 项目学制能从知识库项目名称明确识别时自动计算；无法确认时标记“待补录”，不伪造预计毕业日期。
- 后台「数据中心 → 培养计划」集中显示学制待补录、预计毕业待补录和已完成培养档案的学生；班主任、管理员和领导可直接补录或修正。
- 后台「数据中心 → 学生档案」按“国家/地区 → 留学方案 → 学生”分层展示，可按具体方案和培养状态筛选。在国家或方案进入 Dify 知识库后，刷新页面即可同步到筛选分支。

阶段自动流转 + 人工可调：

- 员工创建申请 → 学生变「申请期」
- 申请必须按八个阶段逐级推进，不能从选校定位直接跳到已入学
- 申请推进到「已入学」→ 自动变「在读」，解锁请假/成绩/售后，并补齐完整前置时间轴

### 智能助手请假的缺失字段与确认

- 正常主链路是：前端 → Dify 意图分类 → LLM 提取类型/日期表达/原因 → `prepare_leave` 日期归一化与草稿检查 → Dify 追问或复述确认 → 用户确认 → `confirm_leave` → FastAPI 最终校验和事务写库。
- Dify 负责语义理解、缺失追问和确认；FastAPI 负责 Pydantic、在读权限、非法日期、重复/重叠和真实提交。后端规则不再提前截断正常请假请求。
- “下周一到下周三”会归一化为具体起止日期并自动计算 3 天；“2026-02-30”会明确返回非法日期，不会静默改成其他日期。
- 开始日期不能早于服务器当天（例如 2026-11-20 不能提交 2026-10-07）；该规则在 `prepare_leave`、降级处理器和正式写库服务三层同时执行。
- 草稿保存在 `leave_request_draft`；信息齐全先返回确认摘要。只有用户明确确认后，`prepare_leave` 才签发 10 分钟有效的一次性确认令牌，`confirm_leave` 校验令牌后才写正式请假单。
- Dify 超时或不可用时才启用后端确定性处理器降级，并在响应中标记 `orchestrator=backend_fallback`。
- 管理员或领导可在「学生档案 → 调整阶段」手动改，变更会通知学生；顾问和班主任无权改学籍阶段。

### 申请案件档案与材料

- 申请时间轴不再只是状态节点；选校、材料、递交、面试、Offer、签证、行前和入学每个阶段都有结构化明细、结论、时间和操作日志。
- 管理端可按阶段完善院校、申请编号、面试、Offer、签证和行前信息；学生端可查看本人当前阶段和全部历史阶段。
- 材料清单支持附件上传、版本、审核通过/退回、审核意见和内部/学生可见范围；单个文件上限 8 MB，文件正文存放在 `backend/uploads/application_materials/`，不写入 SQLite。
- 学生只能在当前阶段或负责人标记为“待补充”的阶段补交材料；已完成历史阶段由员工补档，学生可以查看和下载已公开附件，但不能自行改写历史。
- 早期只有“系统按最终状态补记”的节点会明确标记为“历史回填”，不会把回填状态伪装成真实材料或办理结果。

## 全角色权限

完整矩阵见 [`docs/全角色权限矩阵与验收.md`](docs/全角色权限矩阵与验收.md)。核心边界：

- 顾问、班主任、领导是同一个“员工”账号类型下的三个工作分工，不是三个独立账号类型。
- 管理员登录一次后可在同一后台切换管理员、员工（顾问/班主任/领导）和维护人员视图，无需重新登录。
- 管理员可以管理全部业务、账号和活动；留学方案主数据只从 Dify 知识库读取，后台不提供方案写接口。
- 领导可以查看和推进全部业务，但不能管理账号或修改系统内容。
- 顾问只能处理本人客户线索、本人负责学生的申请、成绩和售后，可只读本人学生预警，不审批请假；可查看活动及本人负责线索的报名名单，并直接进入 CRM 跟进，但没有活动发布权限。
- 班主任只能处理本人班级学生，负责请假、预警、售后和成绩，不访问 CRM，不新增活动或留学方案。
- 员工助手搜索会同时查询学生档案和 CRM 客户线索：学生命中时明确显示学生信息；只有没有学生和线索时才回答未找到。
- 维护人员只能查看健康状态和本人账户，不能读取学生、客户、成绩、请假或预警。
- 这些限制由后端 `backend/service/rbac.py` 与各接口的数据归属校验强制执行，不依赖前端隐藏按钮。

## 内容数据规则

- 活动和留学方案不再由程序启动时自动生成；旧演示活动及报名已清空。
- 当前保留的留学方案均逐条通过 Dify 知识库核验，并记录真实来源文档。
- 活动由内容/运营人员在后台按真实日程新增、修改和删除，保存后公开接口立即更新。
- 客服、官网悬浮助手和学生/员工智能助手询问活动时直接读取 `event_lecture`，后台新增活动后下一次提问立即出现；Dify 客服活动节点使用 `content_events` 当前工具。
- 留学方案只提供 Dify 实时只读接口，后端没有新增、编辑或删除方案的写接口。

## 架构：谁能走智能体，谁走直连

```
浏览器 ──┬─ 官网/客服页 ──→ Dify 客服与活动工作流 ──→ 自定义工具 ──→ 后端 API
         ├─ 学生工作台 ──→ Dify 学生工作流      ──→ 自定义工具 ──→ 后端 API
         ├─ 员工工作台 ──→ Dify 员工工作流      ──→ 自定义工具 ──→ 后端 API
         └─ 后台管理操作 ─────────────────────────────────────→ 后端 API（不经 Dify）
```

约定：**对话型能力**（咨询、查询、提交申请）走 Dify；**管理型操作**（审批、增删改、阶段推进）由后台页面直连后端，保证两套口径一致、权限可控。

```bash

cd docs/dify_dsl
python build_tools.py

# 2. 按意图分支重建三张工作流，输出 live/*_new.json 与 *_workflow.yml
python patch_workflows.py
```

写回 Dify 与验证步骤见 [`docs/dify_dsl/导入说明.md`](docs/dify_dsl/导入说明.md)。三个 App 的真实调用凭据放在被忽略的 `backend/dify_config.local.json`，也可用环境变量覆盖；`backend/dify_config.json` 只是空模板。

### 回复风格：纯文本、不思考、快

三张当前工作流共 31 个唯一 LLM 节点，均关闭了 `enable_thinking`，并追加了「直接回答、不用 markdown 符号」的输出规范。三道闸门：

1. **提示词**（Dify LLM 节点）要求纯文本、直接给结论；
2. **后端** `_clean_answer()` 兜底剥掉 `think` 标签、"正在调用工具"整行、"作为 AI"自述；
3. **前端** `renderMarkdown()` 万一收到 markdown 也渲染成真标题/列表/表格，肉眼不见符号。

需要重做运行库时：

```bash
cd docs/dify_dsl
python patch_workflows.py
python publish_runtime.py --apply
```

实测关闭思考后：学生费用咨询 3.7s、客服材料咨询 4.2s，输出全部是自然分段的中文。

## 注意

- `backend/yuejiao.db` 是运行中的业务库，`schema.sql` 只是建表基线；改表结构请同时更新 `db.py` 的 `MIGRATIONS`，启动时自动补列。
- 项目当前**不是 git 仓库**。若初始化，`.gitignore` 已排除数据库、密钥与 `__pycache__`。
- 登录令牌密钥在首次启动时生成到 `backend/.token_secret`（64 位随机）。修改密码或停用账号会递增 `token_version`，旧令牌立即失效。
- GET 鉴权统一使用 `Authorization: Bearer <token>`，前端不再把 token 放进 URL。
- 情绪预警采用“后端确定性规则优先 + Dify 模型语义兜底”：高危 90 分（严重暴力 100 分）、关注 55 分、积极 15 分、普通 20 分；模型分只能与规则分取较高值，不能降级明确高危。40–69 只记录画像，≥70 才写预警；高危通知按学生绑定班主任、管理员和领导升级发送，同一学生相同原文 10 分钟内去重。模型生成的“已通知老师”承诺会被删除，只展示数据库确认后的真实通知状态。
- 真实 Dify Key 放在被忽略的 `backend/dify_config.local.json`；可提交的 `backend/dify_config.json` 是空模板。
- 登录、注册、密码找回、公开客服、官网留资均配置了进程内滑动窗口限流；登录连续失败第 9 次返回 `429`。
- GET 接口只接受 `Authorization: Bearer`，不再允许把 Token 放进 URL 查询参数。
- 默认 CORS 只允许本机同源页面，不允许 `null/file://` 来源；响应已增加 CSP、`nosniff`、同源 iframe 和 Referrer-Policy 安全头。
- 可运行 `frontend/start_frontend.ps1` 在 `8080` 启动独立前端服务，后端仍在 `8000`；FastAPI 故障时前端页面仍能打开。
- Dify 旧“统一登录与角色路由”应用已停用并关闭 API/Site 入口，当前三张正式工作流保持正常。
